# The lint and the per-config check as defenses, 18 November 2026

This evaluates three checks a benchmark or a deployment could adopt, using the
raw results of census run 43387362408, the census triage in
`results/triage-census.json` and the lint summary in `results/lint_summary.json`.
Nothing new was executed. `tools/defense_eval.py` reproduces every number from
the downloaded census artifacts and writes `results/defense_eval.json`.

The census audited each of the 6,230 accepted best-round kernels at the
benchmark's own shape under up to four autotune configs, with each config forced
in its own process so the autotuner's benchmarking pass did not run. It found 34
defects, which are 29 uninitialized outputs and 5 out-of-bounds reads.

## 1. A dynamic check must cover every config

Each row is a check, run on CPU under the Triton interpreter, and the recall is
over the 34 census defects.

| Check | Defects caught | Recall and 95% interval |
|---|---|---|
| Plain comparison with the reference, config 0 only | 20 of 34 | 58.8%, 42.2 to 73.6 |
| Plain comparison, every config | 25 of 34 | 73.5%, 56.9 to 85.4 |
| Poison fill, config 0 only | 24 of 34 | 70.6%, 53.8 to 83.2 |
| Poison fill and ASan, config 0 only | 27 of 34 | 79.4%, 63.2 to 89.7 |
| Poison fill and ASan, every config | 34 of 34 | 100% by construction |

1. The last row is circular, because the census defined a defect as a kernel this check flags and that triage confirmed. It is an upper bound and not a measured recall. The meaningful result is what is lost by checking fewer configs or using a plain comparison.
2. A check of config 0 alone misses 7 defects even with the poison fill and ASan, which are `160_r2`, `228_r2`, `3828_r2`, `703_r1`, `7485_r3`, `7912_r3` and `825_r3`. 23 of the 34 defects appear under some configs and not others.
3. A plain comparison misses 9 defects even across every config, because on CPU the unwritten region often holds values that happen to match or a zero the reference shares. The poison fill removes that dependence on allocator state.
4. The dynamic check flagged 36 kernels in the whole census, of which 34 were confirmed defects and 2 were triaged as false positives, so its precision is 94.4%.

## 2. The cost of checking every config is small

1. Across all 6,230 kernels the plain and poison runs took 26.5 CPU hours with config 0 only and 32.6 CPU hours with every config audited, which is 1.23 times as much.
2. Among the 1,391 autotuned kernels, the median per-kernel overhead is 3.95 times, from 2.6 to 10.0 seconds, with a median of 4 configs audited.
3. The overhead stays low for the population because 78% of kernels have no autotuning and the census capped the audit at four configs.

## 3. The lint is a cheap static gate

1. The fixed-grid rule marks 304 of the 6,230 accepted best-round kernels, which is 4.9%.
2. It marks 23 of the 29 uninitialized-output defects, which is 79.3% with an interval of 61.6% to 90.2%. It marks none of the 5 out-of-bounds reads, which it is not designed to catch.
3. Its precision is 23 of 304, which is 7.6% with an interval of 5.1% to 11.1%. The rate among unmarked kernels is 6 of 5,926, which is 0.10%, so a marked kernel is about 75 times as likely to carry the defect.
4. The six uninitialized-output defects it misses have a different cause. Four have no autotuning and write through a wrong mask or a wrong grid. `7962_r1` is autotuned and uses a padding-validity mask that is wrong under every config. `1797_r3` is autotuned with a grid that depends on the config and leaks only under config 0, and its cause has not been read yet.
5. Running the per-config check only on lint-marked kernels would cost 2.8 CPU hours instead of 32.6 and would keep 23 of the 29 uninitialized-output defects. A benchmark can use the lint as a triage step and still needs the full check for the other six.

## 4. The source fix works at population scale

1. The fix for the fixed-grid pattern is a grid that reads the winning config, for example `lambda META: (triton.cdiv(n, META["BLOCK_SIZE"]),)`.
2. Among accepted autotuned kernels whose grid already depends on the config, the uninitialized-output rate is 2 of 1,093, which is 0.18% with an interval of 0.05% to 0.66%. That is close to the 0.08% of kernels without autotuning, at 4 of 4,839, and far below the 7.6% of lint-marked kernels.
3. The generation records agree. After a one-of-five failure the model switched to a config-dependent grid in 384 of 453 next rounds, and 311 of those were accepted.
4. This is observational and not a controlled rewrite of the same kernels. A controlled test would apply the fix to the 23 marked defects and rerun the per-config check, which needs the corpus code and so runs on CI.

## 5. What this means for the paper

1. The defense a benchmark should adopt is a per-config check with a poison fill, because a single-config check misses about one defect in five and a plain comparison misses about one in four. It costs about a quarter more CPU time over the population.
2. The lint is a useful cheap filter and a clear rule for code review, but it is not a substitute for the dynamic check.
3. The deployment-side fix is a config-dependent grid, and the data shows it brings the defect rate down to the level of kernels without autotuning.
4. These numbers are on CPU. On a GPU the plain comparison depends on allocator state as well, so the gap between the plain and poison rows may differ there.
