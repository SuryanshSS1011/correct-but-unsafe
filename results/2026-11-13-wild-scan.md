# Scan of hand-written Triton code, 13 November 2026

This file records a static scan of production Triton code for the pattern
that the census found in generated kernels. The question was whether an
autotuned kernel with a grid that cannot follow the chosen config also occurs
in code that people deploy.

**Status:** The scan and the reading are done. Two candidate defects were found
by reading. Their details are withheld from this public file until they are
confirmed and the maintainers have been told.

## 1. Scope

1. GitHub code search reports about 40,768 Python files that contain `triton.autotune`. The first 1,000 results of three queries cover 938 repositories.
2. The scan set has 40 repositories. It combines serving engines, kernel libraries and the largest projects in the search sample. The commit of each one is in `wild/scanset.txt`.
3. Only Python sources were fetched. `tools/scan_repos.py` parses them and executes none of them.

## 3. The six library kernels with no loop

All six were read in full.

1. Two are candidate defects. Both sit in vendor backends of one operator library. One returns a result tensor that is never written on a rarely taken path. The other processes only part of each row when a small tile wins the tuning race. Neither has been confirmed by a run.
2. One is safe because its grid is a cached callable that reads the chosen block size.
3. Three are safe because a pruning callback pins the tuned tile to the tile that the fixed grid assumes.

## 4. What the scan says about the pattern in deployed code

1. The pattern is rare in mature code. Of 1,316 kernels tuned over a size-like parameter, 2 have a candidate defect by reading.
2. Engineers know the hazard and guard against it in three ways. They pass a grid callable that reads the config, they pin the tuned tile with `prune_configs_by`, or they consume the tuned parameter in a loop. SGLang's combine kernel carries the comment "grid is determined by autotune" next to its callable grid.
3. The generated corpora show the pattern far more often. Rule L1 marks 11.3% of Dr. Kernel rounds and 3.2% of Makora programs.

## 5. Limits

1. The 249 loop-class marks were classified by a heuristic and were not read one by one.
2. 596 autotuned kernels take their config list from a helper or from a YAML file. Of these, 117 are launched with a fixed grid and could not be judged.
3. Launch sites are matched to kernels by name, and grids are resolved to the nearest assignment above the launch. Indirect launches are missed.
4. The 15 marks in test code were not triaged.
5. The scan set is 40 repositories out of at least 938.
6. Per-repository counts are in `results/wild_scan_counts.json`. The list of marked kernels is not published yet.
