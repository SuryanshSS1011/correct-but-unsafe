# Cross-request leak check, 19 November 2026

This file asks whether a partial write returns an earlier request's data on a
GPU. `gpu/cross_request_leak.py` plays a server in one process. Request A, the
victim, fills a tensor with the values 4242 + i / n and frees it, as a finished
request does. Request B then runs the fixed-grid add-one kernel of the minimal
demonstration on its own input, with a `torch.empty` output of n = 1,048,576
elements. The script counts how many of B's unwritten elements hold A's values.
It ran through `gpu/modal_leak.py`, three repeats per scenario, with torch
2.15.0. The raw files are `results/raw/a100-leak/gpu_leak.json` and
`results/raw/a100-leak-tuned/gpu_leak.json`.

## 1. With the partial config fixed

B's kernel was forced to its block of 256, which is what a server runs once
its winner is fixed, whether by tuning at startup or by the disk cache after a
restart. It leaves 786,432 of the 1,048,576 output elements unwritten. The run
was on an A100-SXM4-80GB.

| Scenario | B's unwritten elements that hold A's values, each of 3 repeats |
|---|---|
| Same size | 786,432, all at A's positions |
| Unrelated allocations between A and B | 786,432, all at A's positions |
| `expandable_segments:True` | 786,432, all at A's positions |
| A's tensor four times larger than B's | 786,432, at other positions |
| `PYTORCH_NO_CUDA_MEMORY_CACHING=1` | 0, the region is zero |
| A and B in separate processes | 0, the region is zero |

Inside one process, every unwritten element of B's output held the previous
request's data, in every repeat. With the caching allocator, B's output reused
A's freed block. With expandable segments the result was the same. When A's
tensor was larger, B received part of it, so the values came from other
positions of A. A's values are 4242 + i / n in float32, which identifies a
position only to within about 500 elements, so "A's positions" means the
values match A's at the same index after rounding.

Without the cache and across processes the region came back as zeros. A new
allocation from the driver is zeroed, so this check found no leak between
processes. The risk is inside one serving process, where the requests of
different users share the allocator. The unwritten counts in these two rows
are about 786,070 and not 786,432, because the script counts an element as
unwritten when it differs from the correct value, and the correct value of a
few hundred elements is within 1e-3 of zero.

## 2. With tuning after the victim

`--tuned` lets the autotuner choose, and it chose a partial block of 256 in 16
of 18 runs and 512 in the other 2. It tunes inside B, after A has freed its
data, and the benchmark allocates and fills its own buffers. These overwrote
A's freed memory, so B's unwritten elements held neither A's values nor zeros.
This ordering does not occur in a server, which tunes before it serves
requests, so section 1 is the case that matters. The run was on an
A100-SXM4-40GB.

## 3. What follows

A kernel with this defect, deployed in a long-lived process with the default
caching allocator, returns the previous request's data in the elements it does
not write. This is a synthetic server with the study's own kernel, not a
serving engine. A test in vLLM or SGLang, with real requests and CUDA graphs,
is still needed to show the same in a deployed system.
