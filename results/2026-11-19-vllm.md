# Cross-request leak in vLLM, 19 November 2026

This file asks whether a kernel with the study's defect, deployed in a real
serving engine, lets one user's request affect another's. It ran on Penn State
Roar Collab, on an NVIDIA A100-PCIE-40GB with driver 580.178, vLLM 0.34.0,
torch 2.14.0+cu130 and Triton 3.8.0. The model is Qwen2.5-0.5B-Instruct in
bfloat16. The raw files are in `results/raw/roar-vllm/`, and
`python gpu/vllm_leak/summarize.py results/raw/roar-vllm/matrix` prints the
verdicts below.

## 1. Setup

vLLM's `SiluAndMul` allocates its output with `torch.empty` and calls a kernel
on it. A vLLM plugin, `gpu/vllm_leak/cbu_vllm_plugin`, replaced that kernel with
a Triton kernel of the same signature, so the output buffer still came from
vLLM's own allocation. The defective kernel launches a grid computed for a
block of 1024 with a block of 256, the pattern of the accepted corpus kernels.
It leaves three quarters of each output unwritten. The control is the same
kernel with the grid computed from the block, which writes every element. The
defect was placed here for the experiment. vLLM's own kernel does not have it.

In each engine, two synthetic victim prompts, V1 and V2, alternated before the
same 9-token request B, at victim lengths of 24 and 400 tokens, three times
each. Prefix caching was off, so B could not reuse a victim's KV cache.
Decoding was greedy, 16 tokens, with the top 5 log-probabilities at each
position. Each configuration ran in a fresh process.

## 2. B's output

A cell's verdict compares B's output across the six trials. For sequential runs
the output is B's top-5 log-probabilities at every position before the first
NaN, which catches a change that moves the probabilities but not the tokens.
For batched runs it is B's tokens, because batching changes the control's
log-probabilities slightly but never its tokens.

With the correct kernel, B's output did not vary in any of the 18 cells.

| Defective kernel | Victim length | Eager, default allocator | Eager, expandable segments | CUDA graphs, default allocator | CUDA graphs, expandable segments |
|---|---|---|---|---|---|
| Sequential | 24 | determined by victim | NaN | varies with history | varies with history |
| Sequential | 400 | determined by victim | NaN | determined by victim | determined by victim |
| Batched | 24 | varies with history | varies with history | varies with history | varies with history |
| Batched | 400 | determined by victim | varies with history | varies with history | no variation |

**Determined by victim** means that the three trials with the same victim gave
the same output and no output after V1 equaled one after V2. **Varies with
history** means that B's output varied, but not as a function of the last
victim alone. **NaN** means that B's log-probabilities were NaN from the first
position, so the output carries no information either way.

B's output depended on earlier requests in 13 of the 16 defective cells, in 5
of them as a function of the last victim alone. With the default allocator it
did so in all 8 cells. With CUDA graphs and sequential requests, B's output for short
victims differed in all six trials, so state from earlier replays reaches it too. Two cells were
NaN and one did not vary.

## 3. B's activation buffers

In eager mode with the default allocator and sequential requests, the plugin
also copied B's output buffers to the host during B's prefill, with their
addresses. The buffers sat at the same addresses in every trial, so the
unwritten parts of two trials can be compared element by element.

| Unwritten elements that differ between two trials | Same victim | Different victim |
|---|---|---|
| Layer 0, victim of 24 tokens | 0 of 196,608 | 97,821 of 98,304 |
| Layer 0, victim of 400 tokens | 0 of 196,608 | 97,791 of 98,304 |
| All 24 layers, victim of 24 tokens | 0 of 4,718,592 | 2,347,704 of 2,359,296 |
| All 24 layers, victim of 400 tokens | 0 of 4,718,592 | 2,346,984 of 2,359,296 |

B's input to layer 0 is the same in every trial, so the unwritten memory it
reads there can only differ because of what earlier requests left. It was
identical whenever the same victim came before B and 99.5% different when the
other victim did, regardless of the trials before that. The contents of B's
activation buffer are a deterministic function of the previous user's input.

A direct comparison with the victim's tensors was inconclusive. The unwritten
elements at addresses where the victim's MLP input or output had been matched
those values bit for bit no more often than a shifted baseline, 2,880 against
3,312. Something else wrote there after the victim's MLP, most likely its other
tensors. So the result shows that one user's input flows into another user's
activations, not that B's buffer holds a readable copy of a specific tensor of
the victim's.

## 4. Limits

The defect leaves three quarters of each MLP activation unwritten, so B's
output with the defective kernel is nonsense in every cell. A kernel that left
only a small part unwritten, like `2487_r3` with one element, would give
plausible output that still depends on the earlier request, which this run did
not test. These are one model, one GPU type and one engine version. Turning the
allocator cache off entirely was not run, so the second allocator setting is
expandable segments.
