# Controlled test of the grid fix, 19 November 2026

This tests the source fix directly. The 23 lint-marked census kernels that
return uninitialized output were audited twice on CPU, once as accepted and
once with their launch grid rewritten to read the autotuned block, with
`lambda META: (triton.cdiv(n, META["BLOCK_SIZE"]),)` in place of
`(triton.cdiv(n, 1024),)`. Both runs used the per-config check in light mode,
which runs the plain comparison, the bounds oracle and the poison fill on every
autotune config in eval and train mode.

1. Run 44474680089 applied `tools/grid_fixes.json` through `tools/apply_grid_fix.py`.
2. Run 44474692558 ran the same 23 kernels unpatched as the control.
3. `tools/gridfix_compare.py` reproduces every number below and writes `results/grid_fix.json`.

## 1. Which kernels the fix applies to

Eighteen of the 23 have a grid of the form `cdiv(n, CONSTANT)`, so the rewrite
is mechanical. The other five have a grid with one program per row, such as
`(B,)` or `(n_rows,)`, and a kernel that covers `tl.arange(0, BLOCK_SIZE)` of
each row without a loop. When a block shorter than the row wins, the rest of
the row is never written. Their grid is not wrong, so a grid rewrite cannot fix
them. They need a loop over the row or configs pruned to blocks at least as
long as the row. This is the same shape as the `renorm_` bug in the operator
library, and these five are `1915_r3`, `1918_r2`, `2487_r3`, `3008_r2` and
`4314_r4`.

In 12 of the 18 kernels, the grid line carries a comment in the model's own
words saying the autotuner will adjust or override it, for example "initial
grid; autotune will override BLOCK_SIZE". The model believed the tuner resizes
the launch, which it does not.

## 2. Results

1. In the control, all 18 patched kernels had at least one config that left output unwritten, which matches the census.
2. After the fix, 16 of the 18 left nothing unwritten under every audited config in both modes, and every config that ran still matched the reference. That is 16 of 16 among the kernels whose fix is complete and whose configs all ran.
3. `3278_r2` was clean, but only its first config ran in the fixed run before the per-kernel time budget ran out, because the smaller blocks launch four times as many programs under the interpreter. The control ran all six of its configs, three of them partial. It is clean on what was checked and not fully verified.
4. `228_r2` was fixed only in part, as expected. Its partial configs fell from four to two, because the kernel also covers `tl.arange(0, BLOCK_W)` of each row without a loop over the width, so a config with a narrow `BLOCK_W` still misses columns.
5. The five unpatched kernels gave identical results in both runs, which confirms the two runs are comparable.

## 3. What this means

1. The fix is confirmed as a controlled result and not only as an observation. Rewriting the grid removed every partial write in 16 kernels, with no change in output.
2. The fixed-grid lint marks two different bugs. Most marks are a grid that ignores the tuned block, which the rewrite fixes. Some are a row kernel with no loop, which needs a different fix. A lint that reported which of the two it saw would give a more useful repair hint.
3. Both bugs are the autotune blind spot. In each case a config that the tuner may pick leaves part of the output unwritten, and the first call hides it.
